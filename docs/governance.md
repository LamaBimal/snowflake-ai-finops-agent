# Governance

## Access
- Everything was built and runs as `ACCOUNTADMIN`. Before production use, create a dedicated role, for example
  `AI_FINOPS_ROLE`, with:
  - `USAGE` on `AI_FINOPS` and its schemas, and `CREATE TABLE/VIEW/PROCEDURE/TASK/STREAM` on them
  - `IMPORTED PRIVILEGES` on the `SNOWFLAKE` database (or the `USAGE_VIEWER` database role) to read
    `ACCOUNT_USAGE` Cortex views
  - `SNOWFLAKE.CORTEX_USER` database role for `AI_COMPLETE`
  - `EXECUTE TASK ON ACCOUNT` and `USAGE` on `COMPUTE_WH`
- Then transfer ownership of the task graph in one statement (see the snowflake-tasks guidance) so `AFTER` links are kept.
- Dashboard viewers only need `SELECT` on `ANALYTICS.DAILY_METRICS` and the `DETECTION` result tables/views.

## Data handled
- Usage telemetry only: token counts, credits, model names, user IDs, role names, query tags. No prompt or
  response text from production workloads is read.
- The routing eval set is synthetic (generated by llama3.1-70b); it contains no customer data.
- User IDs appear in `V_CORTEX_USAGE` / `V_CORTEX_AGENT_USAGE`; apply a masking policy if the dashboard is shared
  beyond the FinOps team.

## Application attribution
- `APPLICATION` comes from `QUERY_TAG`: a plain string (`rag-support-agent`) or JSON with an `app` key
  (`{"app": "rag-support-agent"}`). Untagged calls appear as `untagged`.
- Agents are attributed as `agent:<db>.<schema>.<name>`, Cortex Search services as `search:<db>.<schema>.<name>`.
- Make tagging a deployment requirement for every AI workload; untagged spend cannot be routed to an owner.

## LLM use
- `AI_COMPLETE` is used only for incident explanations (`llama3.1-70b`, temperature 0, structured output) and
  for building and scoring the routing eval set.
- The model never decides the root cause or the saving estimate (see `architecture/decisions/001`).
- Explanations are stored with the model name and token counts in `INCIDENT_EXPLANATIONS` for audit.

## Change control
- All tasks are created **suspended**; enabling the schedule is a deliberate step.
- The playbook (`RECOMMENDATION_PLAYBOOK`) holds the recommended actions and saving ranges; changes to it change
  what the dashboard recommends and should be reviewed like code.
- Recommendations are advisory; the project does not change any production workload automatically.
